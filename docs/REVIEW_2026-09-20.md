# AURIC work review — 2026-09-20

Today we moved from a large collection of experimental files toward a runnable
development path for a personal coding assistant. The target is a small language
model trained from random weights, developed on CPU now, and sized for a future
2–4 GB VRAM GPU. The assistant is intended to work with project documents,
persistent memory, and tested coding tools.

## What we accomplished

We reviewed the original workspace and found valuable but fragmented work:
custom transformer implementations, several training scripts, tiny JSONL corpora,
retrieval systems, VibeCoder, The Saint, and incomplete or pointer-only model
artifacts. We separated useful infrastructure from claims that had not yet been
validated by a real training run.

We added the `auric/` development path:

- A UTF-8 byte tokenizer with no download or fitted-vocabulary dependency.
- A causal decoder with tied embeddings, scaled-dot-product causal attention,
  gradient checkpointing, and an optional experimental residual gate.
- Correct next-token targets, supervised prompt masking, padding masking,
  grouped train/validation splits, exact deduplication, checksums, and disk-backed
  token blocks.
- CPU-first training with accumulation, clipping, warmup/cosine scheduling,
  validation, deterministic checkpoints, exact CPU resume, and GPU autocast paths.
- SQLite FTS5 document/code retrieval with path and line citations.
- Revisioned project memory requiring explicit evidence and preserving history.
- Read-only source access and reviewable patch proposals.
- A VibeCoder bridge that sends generated code to an isolated runner and fails
  closed when isolation is unavailable.
- Hugging Face metadata inventory and immutable-revision, bounded data fetching.
- Hardware planning, synthetic benchmarks, paired architecture ablations, and a
  31-test correctness suite.

The AURIC work was committed and pushed to
`https://github.com/9x25dillon/patern-coding` while preserving its existing
`MessageVectorizer` project. The merge commit is `82c770f`.

## Evidence from today

The CPU smoke model reduced held-out loss from approximately 5.52 to 3.19–3.23
over 40 steps on a tiny authored corpus. The baseline slightly outperformed the
experimental gate in the paired run, so the gate remains optional. The result
proves that the training path updates, evaluates, saves, and reloads weights; it
does not establish general language understanding or coding ability.

The 2 GB preset has about 10.9M parameters and 512-token context. The 4 GB preset
has about 25.9M parameters and 1,024-token context. CPU forward/backward benchmark
runs completed. Actual GPU fit and throughput remain unmeasured until hardware is
available.

The trained smoke model generated whitespace during a VibeCoder repair episode.
That failure was recorded correctly as `MissingFunction`; the tool loop worked,
but the model is not yet a useful programmer. A hand-authored greeting solution
passed 8/8 VibeCoder cases through the isolated bridge.

## Key decisions

1. Keep the new `auric/` path independent from the older research prototypes until
   an experiment earns integration through measured results.
2. Train from random weights for the core research model. Do not apply LoRA to a
   randomly initialized model; use adapters only when adapting a verified pretrained
   base becomes an explicit, separate goal.
3. Use a byte tokenizer for the first reproducible system. A trained subword
   tokenizer is a later, versioned migration.
4. Treat retrieval, memory, and tool use as inspectable systems around the model.
   Model output is a proposal and never grants permission to run a command.
5. Require grouped held-out splits and record training groups to reduce leakage.
6. Require isolated execution for generated code and fail closed if isolation is
   unavailable.
7. Keep the experimental gate disabled by default until multiple-seed experiments
   on a meaningful corpus show a benefit.
8. Keep generated artifacts, checkpoints, local indexes, and the broader workspace
   out of Git unless they are deliberately curated for publication.

## Unresolved assumptions

- The eventual GPU model, VRAM amount, driver, CUDA version, and PyTorch build are
  unknown. Preset memory estimates exclude activations, runtime overhead, and
  allocator behavior.
- The byte tokenizer is convenient for correctness but inefficient for natural
  language and code. Its byte-level perplexity cannot be compared directly with
  subword-model perplexity.
- The current corpus is far too small for a useful general assistant. More source
  code is not automatically better; provenance, licensing, duplication, secrets,
  and evaluation leakage still need review.
- Lexical BM25 retrieval works immediately but may miss semantically related text.
  Embedding retrieval should be added only with a local model, versioned index, and
  an evaluation set.
- VibeCoder isolation is available on the host, but nested isolation was unavailable
  inside the managed development sandbox. The security properties of each future
  deployment environment must be rechecked.
- The task-group split catches explicit group leakage, not semantic near-duplicates
  or reference answers hidden in prose.
- A small random-weight model may be useful for narrow workflows before it becomes
  a broadly capable coding assistant. Retrieval and deterministic tools will carry
  much of the early usefulness.
- The existing Hugging Face repositories contain useful source and small datasets,
  but repository names and model cards are not proof of complete trained weights or
  data quality.

## Three places I could have been more efficient

1. I spent too much time inspecting broad repository listings before establishing a
   compact decision tree: model code, actual weight files, training data, evaluation,
   and runnable entry point. A smaller first inventory would have shortened the
   review and gotten us to the executable path earlier.
2. I created a substantial first implementation in one pass. The result is useful,
   but a smaller vertical slice—model, one dataset, one training command, one test—
   would have exposed interface issues sooner and reduced later patching.
3. I initialized Git only after the implementation was complete. Creating a clean
   branch and commit boundary before adding the work would have made the later merge
   with `patern-coding` more predictable.

## Three places you could have been more efficient or productive

1. The initial goal combined several ambitions: a novel architecture, a personal
   assistant, retrieval, memory, tools, and a 2–4 GB deployment target. A one-line
   priority order at the start—such as “correct training first, then retrieval,
   then tools”—would have reduced scope ambiguity.
2. Supplying the GPU constraints earlier, along with likely GPU models or a budget,
   would have let us choose a more realistic context length and training schedule.
3. When sharing the GitHub destination, stating whether the remote should be merged,
   replaced, or used as a new branch would have avoided the extra remote-history
   inspection and merge step. The merge preserved both projects, but the policy could
   have been explicit from the beginning.

## Prompting practices that will help

The most useful prompts for this project specify an outcome, a boundary, and an
acceptance test. For example:

> “Implement grouped validation for JSONL records. Do not modify existing projects.
> Add tests for duplicate records, one-group failure, and checksum mismatch. Run the
> focused test suite and report the exact command and result.”

When several goals are present, give them an order:

> “Priority 1: make CPU training correct. Priority 2: add retrieval. Priority 3:
> connect VibeCoder. Defer UI and semantic embeddings. Continue until priorities 1–3
> are tested.”

For experiments, name the comparison and the evidence:

> “Compare baseline and gate with the same seed, corpus, schedule, parameter count
> report, held-out loss, and at least three seeds. Do not call a result an improvement
> unless the evidence supports it.”

For repository work, state the change boundary:

> “Work only in `auric/`, `docs/`, `examples/`, and `tests/`. Preserve all other
> untracked files. Commit the result but do not push until I provide the remote.”

Ask for explicit blockers rather than optimistic completion:

> “If an assumption affects correctness or external state, stop and identify it. For
> everything else, choose a reasonable default and record it in the handoff.”

Useful prompt terms are “acceptance criteria,” “held-out evaluation,” “provenance,”
“reproducible,” “fail closed,” and “scope boundary.”

## Vocabulary to study

**Provenance** — the recorded origin and history of a datum, model, decision, or
result. Example: “Every training record needs provenance so we can trace its source,
license, transformation, and evaluation status.” This helps both of us distinguish
verified evidence from an attractive but unsupported claim.

**Ablation** — an experiment that removes or changes one component while holding the
other conditions fixed, so its contribution can be measured. Example: “Run an ablation
of the coherence gate against the same seed, data, and schedule.” This word makes an
architectural question precise instead of treating a larger system as automatically
better.
